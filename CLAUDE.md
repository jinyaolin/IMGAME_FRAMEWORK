# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm run restart      # Restart the server (./restart-server.sh — uses systemd when available)
npm run kill         # Stop the server (./kill-server.sh — stops systemd unit first)
npm run dev          # nodemon auto-reload — stop the systemd unit first (systemctl stop imgame)
npm start            # Foreground run → http://localhost:3000 (port must be free)
npm run start:lan    # LAN mode via en0 IP (macOS-only command)
```

In production the server runs as the `imgame` systemd service (`/etc/systemd/system/imgame.service`): auto-starts on boot, auto-respawns on crash, logs to `/var/log/imgame.log` (also `journalctl -u imgame`). After code changes, `systemctl restart imgame` (or `npm run restart`) picks them up — there is no build step. Don't start a second server by hand while the unit is active; port 3000 will conflict.

**Production deployment = `https://zaistudio.tw/labs/game`** (Caddy reverse-proxy → :3000, no prefix strip): the whole app mounts under `BASE_PATH=/labs/game` (env; empty = root for local dev), socket.io uses `path = BASE + '/socket.io'`, and clients derive `window.IMGAME_BASE` from `location.pathname` (config.js auto-prefixes absolute `fetch` paths). The merged host+display page `client/labs/index.html` is served at `BASE + '/'`. Login is enforced by `server/auth.js` verifying the main-site `zai_session` HMAC cookie (shared `AUTH_COOKIE_SECRET` in `/root/imgame/.env`, injected via `/etc/systemd/system/imgame.service.d/labs.conf`; unset = auth off for local dev). Host/editor pages + API writes + `join_host` require login; `/mobile` + `/display` + player sockets stay open. Loopback requests without `X-Forwarded-For` bypass auth (AI playtest); Caddy always adds XFF. QR/share links use `PUBLIC_ORIGIN`. Details: `docs/architecture.md` §9.5.

There is no lint setup and no test framework. The `test-*.js` files at the repo root are standalone integration scripts that simulate host/players/display over socket.io-client against a **running server**, so start the server first, then run one directly:

```bash
node test-vote-system.js
```

## What this is

A multiplayer party-game framework: phones (`/mobile`) are private player controllers, a projector (`/display`) is the shared screen, and a host console (`/host`) drives the game. Games ("modules") are authored declaratively in a built-in editor (`/editor`), with global card decks managed at `/decks`. Server is Node/Express + Socket.IO; every client surface is a single self-contained vanilla-JS HTML file under `client/` — no build step, no framework.

Docs: `docs/architecture.md` (developer: classes, socket protocol, lifecycle), `docs/module-authoring.md` (designer: making games in the editor), `README.md` / `README.zh-TW.md` (features, stage/config reference). Root-level `GAME_PARAMS_SYSTEM.md`, `PARAMACTIONS_SYSTEM.md`, `ACTION_BUTTON_MANAGER_README.md` document the newer subsystems. Docs and code comments are largely Traditional Chinese.

## Architecture

### Server core (`server/core/`)

- **`GameSession`** — one per room. Holds players, host/display/player socket ids, `sharedState`, and the loaded module. Routes socket events to the module (`handlePlayerAction`, `handleHostNextPhase`, …) and provides broadcast helpers (`broadcastAll`, `broadcastDisplay`, `sendToPlayer`, `sendToHost`). Handles 30-second disconnect grace and full state restoration on reconnect.
- **`PlayerManager`** — player list. Each player has public fields and private fields (`hand`, `moduleData`); `toPublic()` strips private data for broadcasts, `toPrivate()` goes only to that player. Keep this split intact — leaking `hand`/identity into a broadcast is the classic bug here.
- **`ModuleLoader`** — scans `server/modules/*/manifest.json` into a registry. `load()` resolves the `engine` field to a `server.js` (falls back to `BaseModule`), resolves `{ ref }` deck references via DeckManager, merges host config over manifest defaults, and busts the require cache so edited engine code is picked up per room.
- **`BaseModule`** — the ~2800-line universal game engine (stage state machine, hands, decks, identities, votes, timers). Custom modules put a `server.js` in their directory extending it and override `onStart` / `onPlayerAction` / `onPlayerSubmit` / `onHostNextPhase` / `getGameState` / `getHostState`.
- **`DeckManager`** — CRUD for global decks in `server/decks/*.json` (shared across modules, card image upload).

`server/index.js` (~1100 lines) wires Express routes, the REST API (`/api/rooms`, `/api/modules`, `/api/decks`), all Socket.IO event handlers, and `validateManifest()`.

### Modules = data, engine = code

A game is a `manifest.json` in `server/modules/<id>/` declaring decks, stages, `globalParams`/`playerAttributes`, and `paramActions`. Stage types: `identity_draw`, `card_play`, `vote`, `intermission`, `game` (phones become controllers; optional `gameCode` JS runs on the display canvas via `GameAPI`), `loop` (child stages × N, with `entryCondition`), `goto`, `result`. Each stage has an `advance: { trigger, duration, fallback }` config — the trigger list and behavior live in `BaseModule` (`_scheduleAdvance` and friends).

Derived modules (editor "save as new") reference their parent via `"engine": "<id>"` instead of copying `server.js`, so engine fixes propagate. When a room is created the manifest + engine are deep-clone snapshotted, so editor changes never affect games in progress — only new rooms.

`paramActions` on stages (triggers like `onVoteEnd` firing actions like `storeVoteWinner`, `setValue`, eliminations) are the no-code way to wire vote results → parameters → player elimination; implemented in `BaseModule`.

### Validation is mirrored

`validateManifest()` in `server/index.js` and a client-side mirror in `client/editor/index.html` must stay in sync. Adding a stage type, advance trigger, or manifest field typically means touching: `BaseModule` (runtime behavior), both validators, the editor UI (stage form), and the relevant client surfaces (`client/mobile/game.html`, `client/display/index.html`, `client/host/index.html`).

### Client side

`client/shared/` holds the only shared client code: `socket.js`, `config.js` (custom-IP/QR/lang settings backed by localStorage), and `ActionButtonManager.js` (unified state machine for mobile action buttons, with fallback to the legacy per-stage UI paths). `client/mobile/game.html` implements a strict overlay priority: waiting (didn't ready before start) > eliminated > intermission — lower-priority overlays must never cover higher ones.

### AI core (`server/ai/`)

Kimi (Moonshot) powers two features, wired in `startServer()` via `require('./ai').attach(deps)`:
- **Editor vibe coding** — a chat sidebar in `/editor` (socket events `ai_chat`/`ai_update`) drives an agent loop (`agent.js`) with tools (`tools.js`): read/save/clone manifests (server-side `validateManifest` enforced), read/save engine `server.js`, and `run_playtest` — a headless bot simulation (`playtest.js`) that joins a real room via socket.io-client, plays through stages (confirm identity, play cards, vote), force-advances via host when stuck, and returns an event timeline.
- **AI GM** — a panel in `/host` (`ai_gm_chat`/`ai_gm_toggle`/`ai_gm_update`) with `get_game_state`/`host_action` tools; autopilot subscribes to game events via the `session.aiObserver` hook called from `GameSession.broadcastAll`.

Credentials live in `server/ai/ai-config.json` (gitignored; see `ai-config.example.json`) — endpoint `https://api.kimi.com/coding/v1`, OpenAI-compatible protocol with tool calling, model `k3` (1M context). The manifest schema reference the model relies on is in `prompts.js` (`SCHEMA_DOC`) — **keep it in sync when adding stage types, triggers, or paramActions**, alongside the two validators.

Game-stage `gameCode` may declare `gameConfig.library` (`three`/`babylon`/`p5`); the display lazy-loads the matching UMD bundle from `client/shared/vendor/` before running the code, hands over `GameAPI` (with lazy 2D ctx so WebGL isn't locked, `container` for p5, `onEnd` for cleanup), and `validateManifest` compile-checks `gameCode` on save. Mobile (`client/mobile/game.html`) holds a screen wake lock (Wake Lock API on HTTPS, NoSleep.js fallback on HTTP).

`client/shared/vendor/lowpoly.js` is a procedural fairy-tale character generator (12 roles; `LowPoly.character({role,seed})` → named parts `head/torso/armL/armR/legL/legR/wingL/wingR` + `cape` on hood/robin/witch/wizard/prince/frog/elf — role field `cape:'body'`(same as torso) or a hex; `hairStyle:'princess'|'witch'|'fairy'|'hood'` adds female hairstyles — a side shell (`hairShell`, a wide-arc lathe covering temples+sides+back, face left open) + back-curtain lathe (`hairBack`)+face-framing locks (`hairLockL/R`) for princess/witch, twin buns (`hairBunL/R`) for fairy (wings occupy the back), braids (`hairBraidL/R`) emerging from under the hood for Little Red; the curtain arc (`0.64π`) is the arm-sweep envelope constant shared with capes, feet at y=0) **plus an embedded optional animation layer** in the same file: `LowPoly.animatedCharacter({role,seed})` returns `{root, char, animator}` (game moves `root`, sets facing via `char.rotation.y`, calls `animator.update(dt)`); `animator.play('idle'|'walk'|'run'|'jump'|'attack'|'kick'|'hit'|'emote')` (attack auto-alternates L/R and bakes the side into `animator.current`, a network-syncable string); `animator.busy` gates hit-stun, `animator.progress` polls one-shot progress (0..1). Semantics: trigger names (`attack`/`hit`/…) replay on same-name calls, resolved names (`attackR`/`hurt`/loops — what the network sends) don't; one-shots auto-fall back to the last loop state when finished; walk/run stride frequency follows root horizontal speed (no foot-sliding; fade to neutral at standstill); jump/landing are derived from root.y deltas (vv/air), so display-side code must interpolate snapshot positions before moving root. Capes flutter with zero game code: a 1-DOF underdamped spring (trails with `spd`, lifts when falling, landing recoil emerges — no event channel) plus an analytic traveling wave deforms the ~88 cape vertices every frame. The same system drives back-hair curtains (`hairBack`, princess/witch/fairy — vertex deform) and braids (`hairBraidL/R`, Little Red — a nested kinematic chain where the first `rigidJoints` stay locked to the root so the body-touching draped part doesn't bend into the torso, and only the free tip segments spring toward the previous one, so the tip whips while the base stays put) via a `_flutter` target list; tuning tables `_knobs.cape` / `.hair` / `.braid` (flat shading means no normal recompute needed). Low-level `LowPoly.createAnimator(charGroup, {body, root})` plugs into a game's own rig — body's scale/tilt/y are snapshotted and *composed* (not overwritten), so height-normalization scale may live on `body` or below. Unit regression: `node test-lowpoly-animator.js` (no server needed).

Two sibling vendor globals auto-load **alongside** `lowpoly.js` whenever a `three` game runs (the four loaders — `client/display/index.html`, `client/mobile/game.html`, `client/editor/index.html`, `client/editor/harness.html` — chain `lowpoly.js → fx.js → lowworld.js` after `three.min.js`): `client/shared/vendor/fx.js` exposes `FX` — a lightweight particle/effect engine (`new FX.Manager(scene)` → `spawn/update/kill/clear`, 12 builtin effects in `FX.builders`, `FX.register(name,fn)` for custom, `FX.glowMat/flatMat`); it was lifted out of fairy-brawl, whose `shared/fx.js` is now just the game-specific glue (SKILLS→effect mapping, arena-bound projSpawn). `client/shared/vendor/lowworld.js` exposes `LowWorld` — LowPoly's scenery sibling: seeded, flat-shaded, base-at-y=0 generators `tree(kind:round/pine/fruit)/bush/flowers/grass/house(kind:cottage/thatch/stone/mushroom/twostory — convex overhanging roofs, seed-random wall taper wider-at-base via `o.taper`)/rock/mushroom/fence/cloud` (`LowWorld.create(kind,opts)` + `LowWorld.kinds` for batch), plus one-line wind sway — builders tag swayable foliage nodes with `userData.lwSway` and `LowWorld.wind(scene, t[, strength])` traverses+applies (hard props unaffected). All three (LowPoly/FX/LowWorld) are documented for the AI in `server/ai/prompts.js` `SCHEMA_DOC`. Unit regression: `node test-lowworld.js` (no server needed).

**Physics twin (RL-ready, rig v2, Phase 5 done 2026-07-22, 156/156)**: `LowPoly.physical({role,seed,mode,RAPIER})` → `{root,char,animator,twin,agent,world}` builds a 14-body Rapier ragdoll from `userData.rig`. **The twin's code lives in a separate file `client/shared/vendor/lowphysical.js`** (split out from lowpoly.js so ordinary games — which load only lowpoly.js → fx.js → lowworld.js — never pull in physics; harness/train chain `lowpoly.js → lowphysical.js`). `lowpoly.js` keeps the generator + animator; the rig contract (`userData.rig`: joints/seg/limits/colliders/masses + `torsoSkin`) is the handshake between them (Rapier = vendored `rapier3d-compat.mjs` + wasm, lazy-loaded by callers, never in the auto-load chain). **Masses** (user-tuned, head to 6%, base+limbs heavier): head 1.7 / chest 6.0 / torsoLo 2.0 / pelvis 4.2 / thigh 1.8 / shin 1.3 / foot 1.1 / upperArm 0.6 / foreArm 0.9. **Joint limits enforced on every spherical joint** via rigid **barrier torques** in `applySphTorques` (revolute spine/knee/etc. use Rapier `setLimits` instead); external contact impulses can't push past. The barrier table `LIM_JOINTS` is **derived from `rig.limits`** (chest/neck/shoulder/hip, all three axes) so there is one source of truth — user-specified values are shoulder ±1.75 rad/axis (~200° total) and chest ±1.4 rad x (pelvis-abdomen ±80°/side = 160°). Neck was originally missing from that table, and an unbounded neck is what produced the user-reported stuck pose: an external kick folds `neck.x` to 1.89 rad (108°), the 1.7 kg head hangs the whole chain forward, and straight knees + planted feet wedge the body upright so it never terminates as a fall (2026-07-23; barrier brings it back to 0.66). **Torso is one elastic capsule** (user: "整個身體應該是一塊膠囊"): torsoLo/torsoHi merged into a single `'torso'` Lathe mesh on `spine`, and `animator.skinTorso()` bends its upper vertices toward the `chest` joint each frame (per-vertex slerp from identity, weight 0 at waist→1 at shoulders — a 2-bone linear-blend skin, same idiom as cape/hair `_flutter`); called at the end of `_write` (animated path) AND from `writeBackToVisual` (dynamic physics readback). Physics colliders stay two rigid capsules — RL unaffected. **PD leg gains bumped +12~17%** (hip 620/70, knee 470/30, ankle 620/90) after the mass rebalance made zero-drive squat sag deeper; the env's torque-proxy `KPKD` table mirrors these. 1-DOF joints (spine/elbow/knee/ankle) are revolute + **ForceBased** motors (AccelerationBased is too weak on light limbs — verified); multi-DOF (chest/neck/shoulder/hip) are **spherical + custom quaternion PD impulses** (spacer-chained revolutes leave the spacer's non-driven axis free — the 8.1kg chibi head falls forward through both "satisfied" motors). Standing needs all three of: **foot-plant welds** (contact+low-speed → fixed joint to a static anchor; contact compliance otherwise ratchets feet backward into a forward fall; release when targetSpeed>0.1 AND pelvis walks 0.22m away for 0.15s, else walking deadlocks), **pelvis attitude assist** (up-vector PD torque, `twin.assist` anneal to 0 for pure-physics RL), **preSettle** (pelvis pinned at rest, settle 1.5s, snapshot as spawn/reset point — straight-pose spawn's sag transient gets rectified into a fall).

**Those two props are also why an assisted policy looks like it has no balance reflex** (user, 2026-07-24: "身體往前掉 感覺沒有任何回饋想要平衡的意圖"). Measured, same policy, same 2.4 m/s shove: at `assist=1` the ankle moves 0.07 rad, the hip 0.06, arms 0.25 m/s — the assist torque eats the whole disturbance; at `assist=0` the same policy swings hip 1.73 rad and arms 2.0 m/s. And while standing (`targetSpeed≈0`) both feet are welded *permanently* — a fixed joint guarantees foot speed ≈0 and unbroken contact, so all three release conditions are unreachable (measured: 0/360 frames released, 0.000 m foot travel). Ankle+hip are the only strategies available; **stepping, the one thing that saves a real fall, does not exist mechanically**. Anything evaluated or demoed at an assist level other than the policy's training value is measuring a different system: the harness ran `assist=1` (the default) against policies annealed to 0.4, and `train/watch.mjs` did the same — S0o read 5/20 stuck at assist 1 but **0/20 at its trained 0.4**. Both now take the value explicitly (`POLICIES[].assist` + 輔助 selector; `watch.mjs --assist`).

**Protective stepping** (`LowPoly.physical({protectiveStep: true})`, off by default so existing policies are untouched): the twin now computes a mass-weighted CoM and the **capture point** `CP = com_xz + v_xz/√(g/h)` every step, exposed as `twin.com` / `twin.cp` / `twin.dCP` (distance from the midpoint of the feet) for envs and evals to read. When `dCP` exceeds the support radius (0.14 m) the foot **farther from the CP** — the trailing one, which is the one that should swing — is unwelded, and re-planting is locked out for 0.30 s; without that lockout it re-welds on the very next frame (speed ≈0, contact true) and nothing happens. At `assist=0.4` a shove only reaches `dCP` 0.067 so this never fires; at `assist=0` it reaches 0.361 and the foot travels 0.249 m — a real step. **`reset()`/`restorePose()` must clear the plants** (`clearPlants()`): anchors are world-fixed bodies, so teleporting the character home while a stale anchor holds a foot that had stepped 0.25 m away yanks it back and detonates the ragdoll — the signature is PPO logging `ep_len=1` with value loss at 1.5e5. Engine gotchas (vendored rapier 0.19, all measured): joint anchors are **body-local** not world; `setMass`/`setMassProperties`/`setAdditionalMassProperties` **silently no-op** (only `setDensity` works); queries return null before first `world.step`; collision groups = `(membership<<16)|mask` as one number; spawn-interpenetrating colliders get ejected by contact stabilization (torsoLo/shin fat capsules); capsule feet rock like a rocking horse (use box soles); clamp every explicit torque's per-step Δω (arms hit 154 rad/s in 2 steps unclamped; unclamped assist launched the rig to y=2×10⁶ in the browser). Agent API: `step/observe(53+18 heading-frame, angles wrap-safe)/act(18|24,[-1,1]→limits|2^v kd scales)/reset/contacts/preSettle/setMode/reference`. Harness: `client/editor/lowpoly-rig.html` 物理 select (off/kinematic/dynamic/policy) + 推一把 + obs readout + POLICY_VER label. Full lessons: `docs/reports/lowpoly-skeleton.html` 附錄 C. Regression: `node test-lowpoly-animator.js` (CHECK 16).

**RL training (`train/`, Phase 6 in progress, 2026-07-23)**: pipeline = node physics shards (`train/env_server*.mjs`, NDJSON over stdio, 16 worlds/proc) + PyTorch PPO (`train/ppo.py`, GPU learner, send-all-then-read-all) on **imlab** (`ssh imlab` = 100.94.172.10, 20 cores + RTX 4090, node at `~/opt/node-v20/bin/node`, venv `~/venvs/rl`); rsync `client/shared/vendor/` + `train/` to `~/lowpoly-rl/`, launch with nohup + **pidfile** (never pkill a pattern that appears in your own launch command — it self-matches and kills the launcher; kill by PID number only). ~10k steps/s; 10M steps ≈ 17 min. Action space: 18 joint targets (a=0 = rest pose) + optional 6 damping groups (variable impedance, scale=2^v, `--varimp`/`--act-dims 24`). Results: **M1 stand solved** (M1f: avgTilt 0.094, 0 falls, arms hang via armlock, variable impedance learned — knee kd 0.78→1.63); **M3 reference-free locomotion converging** (M2 imitation line abandoned: the animated gait is march-in-place — passive tracking yields ZERO forward motion — so propulsion can't come from imitation alone; M3 = pure velocity task + linear vz reward + foot-alternation bonus + speed gate). Process management: shard silent deaths hang ppo's read → watchdog 30s select timeout; leaked env servers eat RAM — check `pgrep -f "bin/python train/ppo"` and kill leftovers by PID. Eval: `train/eval.mjs` (stand: falls/avgTilt/tiltDelta), `train/eval_m3.mjs` (locomotion: falls/前進/alternations); deploy = copy ckpt JSON to `client/editor/policy-m1.json` + bump `POLICY_VER` in lowpoly-rig.html. **Stop training with `train/watch.mjs` gates, never fixed steps/sleeps** (`--run <dir-prefix> --kind stand --log <logbase> --pidfile <pidbase>`; `--once --ckpt <file>` runs the gate offline to check its own sensitivity before trusting it). The stand gate is four sub-gates because each earlier one certified something useless: static 20s (0 falls, core-chain <0.12, head <0.15) + pelvis kicks (8 directions, ≤1 fall, ≥6 recover) + **upper-body kicks** (head-fold / head-twist / arm-fling 9 rad/s, ≥3 of 4 recover) + **"推一把" absorbing-state replay** (the harness's exact `(1.8,1.2,1.0)` impulse × 5 × 4 seeds, all must return to pelY>0.42 & core<0.15). That last one is the only sub-gate that catches wedged-upright stuck poses — they are not falls, so falls/tilt metrics all read clean (S0n scored 0 falls / core 0.035 / 8-of-8 pelvis recovery yet 5/20 stuck). The stuck state is chaotic in the initial condition, so the replay must follow the harness flow exactly (fresh rig → 4s settle → 12s observation per push) and sample several seeds. `ppo.py --envargs "…"` passes arbitrary flags straight through to the env shard. ### Conventions

- **Usage log** (`server/usage.js`): successful editor/module/room/AI events append to `data/usage/YYYY-MM.jsonl` (`{t, ev, uid, mod}`) via one `res.on('finish')` middleware + `usage.log()` calls in `host_load_module`, `ai_chat`, and the AI `saveManifest` tool. Loopback (`uid 'local'`, AI playtest bots) is never logged. Report page `/usage` + `GET /api/admin/usage?days=` are superuser-only; names come from zai_studio's SQLite (read-only, handle/display_name). When adding a new write route, add it to the middleware's route table.

- Manifest writes go through `atomicWriteJSON` (tmp file + rename) — do the same for any new JSON persistence.
- Socket protocol (event names/payloads for player/host/display in both directions) is tabulated in `docs/architecture.md` §4; extend it there when adding events.
